# local2: startup ordinal 101 evidence

The 1.26.52.03 screenshot reports an unresolved ordinal 101 while loading `mods/ModMenuBE/ModMenuBE.dll`. The installed local1 binary matched the frozen package: 2,063,872 bytes, SHA-256 `A31CE19C5EB6D18B0D8D8ABE01EB3B42AB461EBA2736C0599B3ACFAA75BEB8F9`.

## Root cause

- The local1 PE import table requests **ordinal 101 from d3d12.dll**, generated by the Windows SDK import library for `D3D12CreateDevice`.
- The test instance's app-local `d3d12.dll` is 104,960 bytes, SHA-256 `FEBC1033EBAF5B017F948A88DE8D29EF694707972D8A7AD943BEAF5EAB26FE25`. Its exports have ordinals 1–7; `D3D12CreateDevice` is ordinal 1, and its entry returns E_FAIL. The same bytes were found in the local 26.45 instance. Its provenance is not inferred from the filename.
- The Windows system copy exports `D3D12CreateDevice` at ordinal 101. The standalone development host used that dependency environment, so its successful rendering did not establish game-instance load compatibility.
- The inspected LeviLauncher native loader uses `LoadLibraryExW` for `preload-native` mods, not an ordinal-101 ModMenu entry. No loader symbol is added to ModMenuBE. The upstream API remains unchanged.

Reference inspected: [LeviLauncher native mod loader at 4c81707](https://github.com/LiteLDev/LeviLauncher/blob/4c81707aeb17e4fb337efc2541922efefcace3bb/native/levilauncher/src/config/mod_loader.cpp). No launcher implementation is copied into this project.

## Fix and regression

Only the overlay's auxiliary D3D12 device creation changes: no eager D3D12 import; obtain the absolute Windows system directory, load its `d3d12.dll`, then resolve **by name**. Keep its module reference for the process lifetime. The game EXE, app-local DLLs, installed settings, native profiles, hooks and public exports are unchanged.

1. `tests/LoaderDependencyTests.py` fails against frozen local1 with `requested=[101], missing=[101]` and passes for local2. The same audit is mandatory at packaging, including delay imports.
2. `D3D12RuntimeTests` verifies the actual function's owning module is the absolute system DLL, both normally and with the instance's app-local DLL already mapped using `DONT_RESOLVE_DLL_REFERENCES`. The app-local fixture's entry point and exports are never executed. No ModMenu initialization or Minecraft startup occurs.
3. Existing settings, resource entry, focus/input, native identity and transaction tests are rerun in Debug and Release. Four exact game versions remain offline profile checks, not gameplay acceptance.

Manual acceptance remains required: launch 26.52 with the new local2 package, verify no ordinal dialog, then main/pause Mods entry and F10. If the process starts but the overlay remains absent, that is a separate runtime result to inspect in its new log; this dependency test does not claim renderer acceptance.
